# Fixes for pipeline-v2.1.0

The brief for building `pipeline-v2.1.0`. It lists what the step-4 dry run on a second Android
project found, and the fix agreed for each. Build the release from this file: each entry says what
to change, and how to check it.

The dry run ran `pipeline-v2.0.0` installed machine-wide (`~/.claude/skills`, `~/.claude/agents`),
with the project's own `.claude/pipeline.md`, and ran the gate on one real branch. Every entry
describes a mechanism, never that project's code, names or paths: this repo is public.

**Release:** all entries go into one minor release, `2.1.0` (new config names and new behaviour;
[`.claude/skills/README.md`](../../.claude/skills/README.md#versions)). Run the golden scenarios
for every stage an entry touches; each must pass 3 of 3.

## 1. Pipeline-owned files are opened by project-relative paths

**Problem.** Skills and agents open files that ship with the pipeline through paths relative to
the project, such as `.claude/skills/pre-pr-checklist/REPORT_FORMAT.md` and
`.claude/PIPELINE_VERSION`. They resolve only when the pipeline is copied into the project. Installed
machine-wide, or as a plugin (step 5), they are missing:

| Reference | Opened by | Effect when missing |
|---|---|---|
| `.claude/skills/pre-pr-checklist/REPORT_FORMAT.md` | `pre-pr-gate` agent | **Seen:** the report used a plain layout, and the agent concluded the skill folder was missing |
| `.claude/PIPELINE_VERSION` | `product-owner`, `architect/PLAN_TEMPLATE.md` | The `pipeline: vX.Y.Z` header of SPEC.md and PLAN.md cannot be filled |
| `.claude/agents/*.md` (named in `developer`, `pre-pr-checklist`) | nobody: agents are started by name | Nothing breaks; the text misleads |

**What the runtime gives.** A loaded skill is told its own folder ("Base directory for this
skill: …"). An agent is not.

**Fix.**
1. **Inline the report format into `agents/pre-pr-gate.md`** and delete
   `skills/pre-pr-checklist/REPORT_FORMAT.md`. The agent then needs no path in any layout, and the
   skill still gives it the feature name and nothing else.
2. **Move `PIPELINE_VERSION` and `CHANGELOG.md` into `skills/`.** A skill reads the version as
   `<its base directory>/../PIPELINE_VERSION`, which resolves in a project install
   (`.claude/skills/`), a machine-wide install (`~/.claude/skills/`) and a plugin (`<plugin>/skills/`).
   Only the skills that write a header need it. Update the release steps in
   `skills/README.md` (and the roll-back command) to the new paths. When the plugin exists, its
   release sets `.claude-plugin/plugin.json`'s version and `skills/PIPELINE_VERSION` together.
3. **The architect opens `PLAN_TEMPLATE.md` from its base directory**, not from
   `.claude/skills/architect/`.
4. **Name agents without a path** ("the `pre-pr-gate` agent").

The one file that stays project-relative is `.claude/pipeline.md`: it is the project's config, not
the pipeline's.

**Checks.**
- A static check in `eval.py`, run with every suite run: fail if any file under `skills/` or
  `agents/` names a `.claude/…` path other than `.claude/pipeline.md`.
- A gate scenario run with the pipeline installed **outside** the project folder (about $5). In step 5
  it becomes the run with the pipeline installed as a plugin.

**Verify in step 5:** that a plugin's skills are told their base directory, like the other step-5
checks in [`HANDOFF.md`](HANDOFF.md).

## 2. The gate diffs against the local base without fetching it

**Problem.** The gate takes its diff and merge-base from the local `{{base}}`. In the dry run the
local base was dozens of commits behind its remote, and the gate noticed only on its own initiative.
With a stale local base:
- the diff can contain changes already on the remote base, so the rule review judges code that is
  not part of the change, and Check 1 sees "unplanned" files
- the pre-flight tests the branch, but not as it would be after merging into the current base
  (a smaller gap; CI catches it)

**Fix.**
1. **Gate: fetch first**, with `git fetch origin {{base}}`. It changes no branch and no working tree,
   only `origin/{{base}}`. If it fails (no network, no auth), go on with the local base and put
   that caveat at the top of the report.
2. **Gate: diff against `origin/{{base}}`.** Use `git diff origin/{{base}}...HEAD` and
   `git merge-base origin/{{base}} HEAD` wherever the gate now uses `{{base}}`.
3. **Gate, Check 4:** report how far behind the branch is ("N commits behind `origin/{{base}}`").
   Merge conflicts with `origin/{{base}}` are a NO GO.
4. **`developer` and `product-owner`:** where they create a branch "from an up-to-date `{{base}}`",
   make it explicit: `git fetch origin {{base}}`, then branch from `origin/{{base}}`. The local
   base no longer needs pulling.

The remote stays hard-coded as `origin`. A config name can be added if a project ever needs
another one.

**Checks.** The gate scenario gets a setup step that leaves the local base a few commits behind its
remote. It passes when the reported diff holds only the branch's own files.

## 3. No early stop when the branch's work is already merged — dropped

**What happened.** The dry-run branch had already been squash-merged into the base. The gate found
that only after the full pre-flight, and returned NO GO.

**Why it is dropped.** The gate runs before a PR exists: the developer skill calls it, or the user
runs it before opening the PR. A merged branch does not reach it in normal use, and when one does,
the verdict is still right, only slow. An early-stop check would be prompt text on every run for a
case that does not occur. Do not raise it again.

**What moves to 11.** The step-4 guide's "a recent, merged or open branch" caused it: the guide
should ask for a branch that is not merged yet.

## 4. No stated behaviour for a branch without SPEC.md / PLAN.md

**When it happens.** Not in the full pipeline: the developer cannot start without PLAN.md. It
happens when `/pre-pr-checklist` is used on its own, on work done without the earlier stages,
which is likely while a team adopts the pipeline one stage at a time.

**Problem.** In the dry run the gate found another document in the feature folder (a working
note) and used its sections as stand-in scope and acceptance criteria. The result was useful, but
improvised: that document is in no contract and may be stale; another run may pick another file or
none, so the same branch can get different reports; and a reader may take "COVERED" as checked
against an agreed spec.

**Fix (`agents/pre-pr-gate.md`).**
- No PLAN.md: Check 1 reports **"Not applicable: no PLAN.md"**, with no stand-in.
- No SPEC.md: Check 2 reports **"Not applicable: no SPEC.md"**, with no stand-in.
- "Not applicable" does not lower the result. Checks 3–5 and the pre-flight decide it as usual,
  and the report's first line says: *"Checks 1–2 not run: no SPEC.md/PLAN.md. This verdict covers
  code quality and CI only, not that the agreed work was done."*
- Other documents in the feature folder may be mentioned, never used as criteria.

Allowing labelled stand-ins was considered and rejected: a gate should be predictable.

**Checks.** A gate run on a branch with no SPEC.md or PLAN.md. It passes when Checks 1–2 say
"not applicable", the first line carries the caveat, and the result comes from Checks 3–5 and the
pre-flight.

## 5. `{{verification}}` cannot express a per-module test task name

**How the value is used.** Only the architect reads `{{verification}}`: it writes the exact command
into each phase of PLAN.md, and the `phase-implementer` agent runs that command from the plan. So
the task name is resolved once, when the plan is written, and the user sees it in the plan review.

**Problem.** The template's value has one `{module}` slot and the same test task in every module.
In a project with product flavours, the unit-test task name depends on each module's flavours (a
module without flavours has `testDebugUnitTest`, one with flavours has `test<Flavour>DebugUnitTest`).
A guessed name gives a plan whose command does not exist, found only when the phase runs. In the
dry run, a hand-written example guessed wrong in exactly this way.

**Fix.**
1. **No new config name.** A project's `{{verification}}` value may carry its own rule in words
   (for example, which task to use by a module's flavours).
2. **`architect`:** one general instruction: *"If a config value has placeholders (`{module}`,
   `{unit-test-task}`, …), resolve each from the project (its build files, or
   `./gradlew :{module}:tasks --all`) and write the exact command. Never guess. If one cannot be
   resolved, ask."*
3. **`phase-implementer`:** if the verification command fails because a task does not exist,
   return **BLOCKED** with the error, and do not substitute another task. A wrong command in the
   plan is a planning error the user should see.

A dedicated name (`{{unit-test-task}}`) was considered and rejected: every project would fill it,
also where the task never varies, and it would cover only this one case.

**Checks.** The template has one task name, so the suite cannot exercise this: the architect and
developer scenarios must still pass (no regression). The real test is the first feature planned on
a flavoured project (step 6).

## 6. The coding rules are assumed to be `CLAUDE.md` sections

**Where it is assumed.**

| Who | Assumption |
|---|---|
| `pre-pr-gate` (Check 5) | Reviews "the rules in CLAUDE.md that the toolchain cannot check"; `{{rule-review}}` is described as `CLAUDE.md` sections |
| `architect` | Reads `CLAUDE.md` first; the plan follows "the `CLAUDE.md` rules"; every code block is held to `CLAUDE.md` |
| `developer`, `phase-implementer`, `product-owner` | "Read `CLAUDE.md`" before starting |
| `retrospective` | Routes "a rule about the code" to `CLAUDE.md` |

**Problem.** Some projects keep no rules in `CLAUDE.md`: it imports an agents file holding the hard
rules, which indexes a docs folder that the project names as the single source of its conventions.
Then:
- **reading:** a skill or agent that reads `CLAUDE.md` with the Read tool does not follow its
  imports, so it sees an overview, not the rules (the main session loads imports automatically;
  a file read does not)
- **rule review:** works only because `{{rule-review}}` can name files; the wording still says
  `CLAUDE.md` sections
- **writing:** the retrospective would add rules to `CLAUDE.md`, where such a project says not to

**Fix.** Two new config names, on the pattern of `{{architecture-rules}}` /
`{{architecture-rules-home}}`:

| Name | Meaning | Template value |
|---|---|---|
| `{{rules}}` | The files holding the project's coding rules, read before planning or writing code | `CLAUDE.md` |
| `{{rules-home}}` | Where a new coding rule is written | `CLAUDE.md` |

- `architect`, `developer`, `phase-implementer`, `product-owner`: "Read `CLAUDE.md`" becomes
  "Read `{{rules}}`"; "the `CLAUDE.md` rules" becomes "the rules in `{{rules}}`".
- `pre-pr-gate`: reviews "the rules `{{rule-review}}` names (sections or files)". `{{rule-review}}`
  stays its own name: the subset no tool checks, which keeps the review short.
- `retrospective`: a rule about the code goes to `{{rules-home}}`.
- `.claude/pipeline.md`: add both rows; reword `{{rule-review}}`'s meaning to "sections or files".

Rejected: no new names, with skills told to follow every file `CLAUDE.md` imports or points to.
It relies on links being followed reliably, and does not tell the retrospective where to write.

**Checks.** The template values stay `CLAUDE.md`, so behaviour here does not change: the
product-owner, architect, developer and gate scenarios must still pass 3 of 3. A project whose rules
live elsewhere is tested in step 6.

## 7. A project with no formatter: the config has no defined `none`

**Where the formatter is used.**

| Who | Text | With the value `none` |
|---|---|---|
| `developer`, PR step | "**Always** run `{{format-fix}}` and commit any files it reformatted." | Undefined: it may run "none", stop, or skip, and runs can differ |
| `pre-pr-checklist`, fix limits | "{{formatter}}: run `{{format-fix}}`." | Harmless: that failure cannot occur |
| `pre-pr-gate`, reading the pre-flight | "The {{formatter}} step: the caller runs `{{format-fix}}`" | Harmless, for the same reason |
| report format (inlined into the gate by 1) | Example line `✅ spotless · konsist · test · assemble · lint   PASS` | Names steps the project does not run; the agent may copy them |

**Problem.** The config has no defined way to say "this project has no such tool". The same gap
applies to lint (8), and to `{{architecture-rules}}` and `{{review}}` in a project without them.

**Fix.** One general rule, not one per tool.
1. **`.claude/pipeline.md` header**, next to "Every value is required": *"A value of `none` means
   the project has no such tool: a step that uses it is skipped, and the stage's report says so.
   `none` is not empty: an empty or missing value still stops the stage."*
2. **`developer`:** "If `{{format-fix}}` is not `none`, run it and commit any files it reformatted."
3. **`pre-pr-gate`** (and the `pre-pr-checklist` fix limits): skip any tool whose value is `none`.
   The report's pre-flight line is built from the actual `{{pre-flight}}` steps, never a fixed list;
   the example becomes generic (`✅ {each pre-flight step}   PASS`).
4. **Mark which names may be `none`**, in `pipeline.md`'s table: `{{formatter}}`, `{{format-fix}}`,
   `{{architecture-rules}}`, `{{architecture-rules-home}}`, `{{review}}`, `{{review-prompt}}`,
   `{{rule-review}}` (Check 5 is then skipped and the report says so), `{{residue-extra}}`, and `{{lint}}`
   (8). The others (`{{base}}`, the prefixes, `{{feature-docs}}`, `{{hosting}}`,
   `{{pre-flight}}`, `{{verification}}`, `{{rules}}`, `{{rules-home}}`) may not.

**Checks.**
- A static check in `eval.py`: every `{{name}}` used in `skills/` and `agents/` is in
  `pipeline.md`'s table, and every name that may be `none` is marked so.
- A gate run (about $5) with formatter, format-fix and architecture-rules set to `none`. It passes
  when the gate skips those steps, says so, and invents no step.

## 8. Lint and `warningsAsErrors` are hard-coded in skills

**Where.**

| Who | Text |
|---|---|
| `architect` | A phase touching a composable or `res/` adds `lint` to its verification, "and it runs with `warningsAsErrors`"; each resource is added in the phase that first uses it, because "an unused resource is itself a lint error"; the self-check asks "run `lint` if it touches UI or res/?" |
| `architect/PLAN_TEMPLATE.md` | `{{verification}}        # add lint if UI or res/ changed` |
| `pre-pr-checklist`, fix limits | "**Lint** (`warningsAsErrors`): fix the cause. No baseline or suppression without asking." |
| `retrospective` | "an {{architecture-rules}} rule … or a lint rule" (stays: a valid destination where a project has custom lint rules) |

**Problem.** In a project whose CI runs no lint, or does not fail on warnings, the architect still
adds a slow lint task to every UI phase (one that may fail on existing warnings CI never sees), and
splits resources across phases to avoid an error that cannot occur. Plans get longer and slower for
nothing.

**Fix.** One new config name, which may be `none` (7):

| Name | Meaning | Template value |
|---|---|---|
| `{{lint}}` | The lint task a phase adds when it touches UI or resources, and whether warnings fail it | `./gradlew lint`, warnings fail (`warningsAsErrors`) |

- `architect`: "If `{{lint}}` is not `none` and the phase touches UI or `res/`, its verification
  adds `{{lint}}`." The add-each-resource-where-first-used rule applies only when `{{lint}}` says
  warnings fail. Same for the self-check.
- `PLAN_TEMPLATE.md`: `# add {{lint}} if UI or res/ changed (unless none)`.
- `pre-pr-checklist`: the fix limit reads "Lint (`{{lint}}`)", skipped when `none`.
- `retrospective`: unchanged.

`{{lint}}` is the per-phase check only. Where CI runs lint, `{{pre-flight}}` already includes it,
as in the template; a project changes both together.

**Checks.** The template value keeps today's behaviour: the architect and developer scenarios must
still pass. A static check in `eval.py`: no file under `skills/` or `agents/` names `lint` or
`warningsAsErrors` except through `{{lint}}` (the retrospective's "lint rule" excepted).

## 9. GitHub (`gh`) is hard-coded in four skills

**Where.**

| Skill | GitHub-only text | GitLab equivalent |
|---|---|---|
| `developer` | `gh pr create --base {{base}} …` | `glab mr create --target-branch … --title … --description …` |
| `review-triage` | inline comments through `gh api …/pulls/{n}/comments`, replies through `…/comments/{id}/replies` | a different model: discussions holding notes (`glab api projects/:id/merge_requests/:iid/discussions`), replies posted to a discussion, another position format |
| `retrospective` | review comments, summary and diff through `gh api` and `gh pr diff` | the same discussions API, and `glab mr diff` |
| `product-owner` | input "a GitHub issue number", `gh issue view {n} --comments` | see `{{issues}}` below |
| `architect` | Mermaid "renders on GitHub" | wording only: GitLab renders Mermaid too |

**Problem.** `{{hosting}}` can only say "anything but GitHub: stop". On a GitLab project the gate
works (it uses no hosting command), but the developer's PR step, review-triage and the
retrospective stop.

**Fix.**
1. **Per-host steps in the skills**, chosen by `{{hosting}}`: "GitHub: … / GitLab: …". Any other
   value still stops. The knowledge stays in the skill and only the choice is config, the lesson of
   step 3. The skills keep saying "PR"; on GitLab it means the merge request (say so once in
   `skills/README.md`).
   - `developer`: a GitLab step to create the MR.
   - `review-triage`, `retrospective`: GitLab steps to read discussions and their positions, reply
     to a discussion, and read the diff.
   - `architect`: drop "on GitHub".
2. **A new name, `{{issues}}`**, because the issue tracker is not always the code host (a project
   may keep its tickets in a separate tracker such as Jira). Values: `GitHub issues (gh)`,
   `GitLab issues (glab)`, or `none` (the user pastes the text, which always works).
   `product-owner` reads its input from it. Other trackers (Jira through `acli`) are a later value:
   the template cannot test them.
3. **`.claude/pipeline.md`:** `{{hosting}}`'s meaning lists the supported values (GitHub, GitLab);
   add `{{issues}}`.

Rejected: a config name per hosting command. The two comment APIs differ in shape, which a config
value cannot express.

**Checks.**
- The developer and product-owner scenarios must still pass (the GitHub path).
- A static check in `eval.py`: every `gh` and `glab` call in `skills/` and `agents/` is inside the
  section for its host.
- **The GitLab steps cannot be run by the suite:** the template is on GitHub, and review-triage and
  retrospective have no scenarios. They are first run in step 6, on a GitLab project. The
  CHANGELOG entry says "GitLab support: written, not yet run" until then.

## 10. A CI check that scans AI-instruction folders on disk sees the local pipeline files

**What happened.** The project's pre-flight included a CI script that checks AI-instruction files
for path references that do not exist. It finds the files by a pattern on disk, not through
`git ls-files`, so it also read the local, uncommitted `pipeline.md`. Had that file named a path
the project does not have (the template's own `pipeline.md` names several), the pre-flight would
have failed locally only: a NO GO that CI never shows, with a cause that looks like the code's. It
passed because `pipeline.md` was written with the check in mind.

**When it matters.** During a dry run, while the pipeline files are local. From step 6 the
project commits `pipeline.md`, so CI sees it too and the two agree. What lasts: in a project with
such a check, `pipeline.md` must pass the project's own checks.

**Fix (docs only).**
1. **`STEP4_GUIDE.md`:** after writing `pipeline.md`, run any CI check that reads AI-instruction or
   docs files, and reword `pipeline.md` until it passes. The project's code stays as it is.
2. **`.claude/pipeline.md` header:** "Write values as plain names and commands. Name a path only if
   it exists in this project."
3. **Step 6 notes** (plugin install): committing `pipeline.md` puts it under the project's own
   checks.

**Checks.** None: it depends on a project's own CI, which the template does not have.
